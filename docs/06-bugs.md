## BUG-01. Двойной клик «Отправить» — покупатель получает два одинаковых ответа

**Симптом.** В переписке два одинаковых сообщения оператора с разницей в доли секунды.
Заглушка площадки записала две отправки.

**Как воспроизвести.** Два запроса ответа в один чат подряд или параллельно: без ключа оба
проходят. На фронте блокировка кнопки через `setSending(true)` срабатывает только после
перерисовки.

**Причина.** У запроса ответа не было идентификатора намерения. Сервер не мог отличить
повтор от нового ответа, а блокировка кнопки работала только после перерисовки.

**Исправление.**
- API: обязательный заголовок `Idempotency-Key`, уникальный индекс `(chat_id, idempotency_key)`,
  порядок «резерв строки → вызов площадки → commit» (ADR-0003). Повтор возвращает то же
  сообщение с `duplicate: true`.
- Фронт: синхронная защита через `useRef` и один ключ на текст ответа; новый ключ — после
  успешной отправки или правки текста (BUG-09).

**Регрессионные тесты.**
- [`test_bug01_same_key_twice_sends_once`](../backend/tests/integration/test_chats_api.py)
- [`test_bug01_concurrent_requests_with_same_key_send_once`](../backend/tests/integration/test_chats_api.py) —
  два потока, барьер, задержка площадки 200 мс
- [`review-findings.test.tsx` — «CR-13: два submit до перерисовки — один запрос»](../frontend/src/__tests__/review-findings.test.tsx).
  Прежний тест на двойной клик проходил и без защиты — см. CR-13.

## BUG-02. Лента сортируется неправильно: чаты Ozon «выше», чем должны

**Симптом.** Сообщение, пришедшее на Wildberries в 21:00 UTC, в ленте ниже сообщения Ozon,
пришедшего на полчаса раньше.

**Как воспроизвести.** Сообщение на Wildberries в 21:00 UTC и на Ozon в 20:30 UTC (23:30 MSK):
при отброшенной зоне Ozon оказывается выше.

**Причина.** Площадки отдают время по-разному: Wildberries — `...Z`, Ozon — `+03:00`,
Яндекс Маркет в заглушке — без зоны (по документации московское). Разбор делал
`datetime.fromisoformat(...).replace(tzinfo=None)` и колонка была без зоны: в БД лежало
«настенное» время разных зон вперемешку.

**Исправление.** `parse_marketplace_ts` приводит любое время к UTC, наивное время получает зону
площадки. Колонки — `timestamptz`, соединение с БД в UTC, API отдаёт `+00:00`. Фронт показывает
время в зоне оператора через `Intl.DateTimeFormat`.

**Регрессионные тесты.**
- [`test_bug02_feed_sorted_by_real_time_across_zones`](../backend/tests/integration/test_chats_api.py)
- [`test_bug02_order_across_marketplaces_follows_real_time`](../backend/tests/unit/test_timestamps.py)
- [`format.test.ts`](../frontend/src/__tests__/format.test.ts)

## BUG-03. Повторная синхронизация дублирует сообщения, а наш ответ появляется дважды

**Симптом.** После второго нажатия «Обновить» в чатах по две копии каждого сообщения покупателя.
Ответ оператора после синхронизации виден дважды: локальная строка и копия с площадки.

**Как воспроизвести.** Синхронизация дважды подряд; ответ из SellerDesk и затем синхронизация.

**Причина.** Сообщения вставлялись простым `INSERT` без ключа. У нашего ответа не сохранялся
внешний id, который площадка присвоила при отправке, поэтому совпадение было не по чему найти.

**Исправление.** Уникальный индекс `(chat_id, external_id)` и `ON CONFLICT DO NOTHING`.
После отправки ответа в строку пишется `external_id` из ответа площадки.

**Регрессионные тесты.**
- [`test_bug03_repeated_sync_creates_no_duplicates`](../backend/tests/integration/test_sync.py)
- [`test_bug03_operator_reply_is_not_duplicated_by_sync`](../backend/tests/integration/test_sync.py)

## BUG-04. XSS: HTML из текста отзыва исполняется в карточке

**Симптом.** Отзыв `Отличная лампа <img src=x onerror=alert('xss')> всем советую` вызывает
всплывающее окно при открытии раздела отзывов.

**Как воспроизвести.** В детерминированный сид заглушки специально добавлен отзыв с разметкой;
e2e на раздел отзывов ловит `dialog`.

**Причина.** Чтобы сохранить переносы строк, текст отзыва выводился через
`dangerouslySetInnerHTML` с заменой `\n` на `<br>`.

**Исправление.** Компонент `UserText` выводит текст обычным текстовым узлом, переносы — через
CSS `white-space: pre-line`. В ESLint добавлено правило, запрещающее `dangerouslySetInnerHTML`
во всём фронте. API отдаёт текст как есть: экранирование — задача места вывода.

**Регрессионные тесты.**
- [`UserText.test.tsx`](../frontend/src/__tests__/UserText.test.tsx) — нет `<img>`, нет `<br>`
- [`feedback.spec.ts` — «BUG-04: разметка в тексте отзыва показывается текстом»](../e2e/tests/feedback.spec.ts)
- правило `no-restricted-syntax` в [`eslint.config.js`](../frontend/eslint.config.js)

## BUG-05. Шаблон с `{{Buyer_Name}}` уходит покупателю буквально

**Симптом.** Покупатель получил «{{Buyer_Name}}, спасибо за отзыв». Правило «не подставилось —
не отправляем» не сработало.

**Как воспроизвести.** Шаблон `{{Buyer_Name}}, спасибо` с узкой регуляркой: текст уходит как есть.

**Причина.** Регулярное выражение искало только `\{\{([a-z_]+)\}\}`. `{{Buyer_Name}}` и
`{{ product }}` не считались переменными: не подставлялись и не попадали в список
неподставленных, поэтому проверка безопасности их пропускала.

**Исправление.** Имена переменных регистронезависимы, пробелы внутри скобок допустимы. После
подстановки текст ещё раз проверяется на остатки `{{` и `}}` — сломанная разметка тоже
блокирует отправку. При создании шаблона неизвестные переменные отклоняются (400).

**Регрессионные тесты.**
- [`test_bug05_variable_in_other_case_is_substituted`](../backend/tests/unit/test_templating.py)
- [`test_bug05_missing_variable_in_other_case_blocks_sending`](../backend/tests/unit/test_templating.py)

## BUG-06. Потерянное подтверждение площадки — второй ответ покупателю (CR-01)

**Симптом.** Площадка приняла ответ, но ответ на HTTP-запрос не дошёл (таймаут). Оператор видит
ошибку, жмёт «Отправить» ещё раз — покупатель получает два одинаковых сообщения.

**Как нашли.** Ревью Codex. Воспроизвёл заглушкой, которая принимает сообщение и один раз
бросает `TimeoutError`: в `sent_log` две отправки.

**Причина.** Ключ идемпотентности жил только в нашей БД. Ошибка площадки откатывала резерв,
ключ освобождался, повтор звал площадку снова — а площадке ключ не передавался.

**Исправление.** `MarketplaceClient.send_chat_message` принимает `idempotency_key`; заглушка
принимает один ключ один раз и на повтор возвращает уже принятое сообщение. В каркасах настоящих
адаптеров — TODO: передать ключ или искать своё сообщение в выгрузке перед повтором.
Для отзывов находка не подтвердилась: у отзыва одно поле ответа, повтор его перезаписывает.

**Регрессионные тесты.** [`test_cr01_*`](../backend/tests/integration/test_review_findings.py),
[`test_cr01_same_key_is_accepted_once`](../backend/tests/unit/test_mock_marketplace.py)

## BUG-07. Поздний AI-черновик попадает в другой чат (CR-02)

**Симптом.** Оператор запросил черновик в чате Анны и сразу открыл чат Бориса. Через секунду в поле
ответа Борису появляется текст, написанный для Анны. Один клик — и он уйдёт не тому покупателю.

**Как нашли.** Ревью Codex. Воспроизвёл в Vitest: отложенный ответ `chatDraft(A)`, открыть Б,
вернуть ответ А — текст А в поле Б.

**Причина.** Результат запроса записывался в общее состояние черновика без проверки, какой чат
открыт сейчас.

**Исправление.** Запоминаю id чата на момент запроса и применяю ответ, только если открыт он же.
Черновик и так сохранён сервером в карточке своего чата. То же для ответа шаблоном.

**Регрессионный тест.** [`review-findings.test.tsx` — CR-02](../frontend/src/__tests__/review-findings.test.tsx)

## BUG-08. После перезапуска API ответ падает на уникальном индексе (CR-03)

**Симптом.** После перезапуска бэкенда первый ответ в чат, где уже был ответ, возвращает 500, хотя
площадка сообщение уже приняла.

**Как нашли.** Ревью Codex. Воспроизвёл сбросом кэша клиентов площадок между двумя ответами:
`UniqueViolation` на `uq_messages_chat_external`, ключ `oz-out-1`.

**Причина.** Заглушка выдавала внешние id из счётчика в памяти процесса. После перезапуска счётчик
начинался с 1, а строки с такими id уже лежали в БД.

**Исправление.** Внешний id заглушки — UUID, как у настоящей площадки.

**Регрессионные тесты.** [`test_cr03_external_id_survives_restart`](../backend/tests/integration/test_review_findings.py),
[`test_cr03_external_ids_unique_across_restarts`](../backend/tests/unit/test_mock_marketplace.py)

## BUG-09. Правка текста после ошибки — новый ответ молча теряется (CR-05)

**Симптом.** Отправка упала по сети, но сервер ответ сохранил. Оператор поправил текст и отправил
снова. Интерфейс показал «Ответ отправлен», а покупатель получил только первый вариант.

**Как нашли.** Ревью Codex. Воспроизвёл: тот же ключ с другим текстом — 200 и старое сообщение;
на фронте после правки уходил прежний ключ.

**Причина.** Ключ был привязан к «намерению», а не к тексту, и сервер не сравнивал текст при
совпадении ключа.

**Исправление.** Фронт: ключ привязан к тексту, правка даёт новый ключ. Сервер: тот же ключ с
другим текстом — 409.

**Регрессионные тесты.** [`test_cr05_same_key_other_text_is_conflict`](../backend/tests/integration/test_review_findings.py),
[`review-findings.test.tsx` — CR-05](../frontend/src/__tests__/review-findings.test.tsx)

## BUG-10. Две одновременные «Обновить» создают две задачи синхронизации (CR-06)

**Симптом.** Два оператора нажали «Обновить» одновременно — в `sync_jobs` две активные задачи,
площадки опрашиваются дважды.

**Как нашли.** Ревью Codex. Воспроизвёл: транзакция А вставила задачу и не закоммитила,
транзакция Б в это время вызывает `enqueue_sync` — создаётся вторая.

**Причина.** `SELECT ... FOR UPDATE` блокирует найденные строки, но не защищает их отсутствие:
оба запроса видели пустую выборку.

**Исправление.** Частичный уникальный индекс «одна активная задача» (`status IN ('queued',
'running')`, миграция 0002) и `INSERT ... ON CONFLICT DO NOTHING`; при конфликте возвращается
существующая задача. Заодно зависшая задача старше 600 с помечается `failed` (CR-07).

**Второй круг ревью исправления** (R2-01…R2-04, таблица в [04-ai-development.md](04-ai-development.md))
нашёл в нём три дыры и слабый тест:

- между конфликтом вставки и выборкой активная задача могла завершиться — `NoResultFound`;
  теперь вставка и выборка повторяются в цикле;
- миграция 0002 падала на уже существующих дублях — теперь перед индексом она закрывает
  лишние активные задачи;
- обработчик задачи, закрытой как зависшая, оживлял её (`failed → running`) — теперь захват
  и запись итога условные;
- тест гонки синхронизировался по `join(timeout)`; теперь — по состоянию сессии B в
  `pg_stat_activity`, без таймаутов.

**Регрессионные тесты.** [`test_cr06_concurrent_enqueue_creates_one_job`](../backend/tests/integration/test_review_findings.py),
[`test_cr07_stale_job_does_not_block_sync`](../backend/tests/integration/test_review_findings.py),
[`test_r2_01_active_job_finished_between_conflict_and_select`](../backend/tests/integration/test_review_findings.py),
