# ADR-0002. Интеграция с площадками: адаптер + фоновая синхронизация в свою БД

- Статус: принято
- Дата: 2026-10-21

## Контекст и проблема

Кабинеты площадок отвечают медленно (в заглушке 800 мс на вызов, у настоящих — секунды
и ограничения частоты). Если интерфейс будет ходить в площадку на каждое открытие ленты, оператор
продолжит ждать, как в кабинетах. Площадок три, API у них разные.

## Варианты

1. Прокси: каждый запрос интерфейса — запрос в площадку.
2. Фоновая синхронизация в свою БД, интерфейс читает только БД.
3. Вебхуки площадок.

## Решение

Вариант 2 за единым интерфейсом `MarketplaceClient`:

```python
class MarketplaceClient(Protocol):
    code: Marketplace
    def fetch_chats(self) -> list[ChatDTO]: ...
    def fetch_feedback(self) -> list[FeedbackDTO]: ...
    def send_chat_message(self, chat_external_id: str, text: str) -> SentMessage: ...
    def answer_feedback(self, feedback_external_id: str, text: str) -> None: ...
```

- Адаптер отвечает за формат площадки, в том числе за разбор времени в UTC (`parse_marketplace_ts`).
- Синхронизация пишет upsert-ом: чаты и отзывы — `ON CONFLICT (marketplace, external_id) DO UPDATE`,
  сообщения — `ON CONFLICT (chat_id, external_id) DO NOTHING`. Повтор безопасен (BUG-03).
- «Обновить» ставит задачу (`sync_jobs`) и отвечает 202, активная задача одна.
- Отправка ответа идёт в площадку синхронно: оператор должен знать, что ответ принят.

Вебхуки (вариант 3) есть не у всех площадок и не для всех событий; их можно добавить поверх,
они будут писать тем же upsert-ом.

## Последствия

- Плюс: лента не зависит от скорости площадки (NFR-01, проверяется тестом).
- Плюс: добавить площадку — написать один класс; сервисы не меняются.
- Минус: данные отстают на период синхронизации. В интерфейсе видно время последнего обновления.
- Минус: в демо задача идёт в `BackgroundTasks` процесса API. Для продакшена нужен отдельный
  воркер с расписанием и ретраями (например, очередь на PostgreSQL или Redis).
