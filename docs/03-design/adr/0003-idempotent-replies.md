# ADR-0003. Ключ идемпотентности для ответов покупателю

- Статус: принято, дополнено 2026-11-03 по ревью Codex
- Дата: 2026-10-24

## Контекст и проблема

Ответ покупателю нельзя отозвать. Двойной клик, ретрай после таймаута или повтор запроса
прокси не должны давать второй ответ (BUG-01). Блокировка кнопки на фронте помогает только от
двойного клика и только в одном окне.

## Варианты

1. Только блокировка кнопки во время отправки.
2. Дедупликация по тексту: тот же текст в тот же чат за N секунд — дубль.
3. Ключ идемпотентности от клиента (`Idempotency-Key`) с уникальным индексом в БД.

## Решение

Вариант 3 вместе с вариантом 1.

- Заголовок `Idempotency-Key` обязателен для `POST /api/chats/{id}/reply` и `/template-reply`.
- Уникальный индекс `(chat_id, idempotency_key)` в `messages`.
- Порядок: `INSERT ... ON CONFLICT DO NOTHING RETURNING id` → вызов площадки → `COMMIT`.
  Параллельный запрос с тем же ключом ждёт на индексе, пока первый не завершится, и получает
  готовое сообщение с `duplicate: true`. Если площадка отказала, транзакция откатывается и ключ
  свободен для повтора.
- Ключ передаётся площадке (`send_chat_message(..., idempotency_key)`): если площадка приняла
  ответ, а подтверждение потерялось, повтор не создаёт второе сообщение (BUG-06, по ревью Codex).
- Тот же ключ с другим текстом — 409: молча вернуть старый ответ значит потерять новый (BUG-09).
- Фронт держит один ключ на текст ответа и меняет его после успеха или правки текста.

Дедупликация по тексту (вариант 2) отбросила бы законный повтор одинакового ответа.

## Последствия

- Плюс: один ответ на ключ при любом числе повторов (тесты `test_bug01_*`).
- Минус: транзакция открыта на время вызова площадки. Для демо приемлемо; при больших задержках
  нужен статус `sending` и отдельная фиксация резерва.
- Ответ на отзыв защищён иначе: условный UPDATE `WHERE answer_text IS NULL`, второй ответ — 409.
